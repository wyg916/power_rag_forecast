# P6 UI 优化前必读总 SKILL

## 0. 文件定位

本文件是智能运营分析项目 P6 UI 优化的统一入口文件。它把两个核心资料合并成一个“每次优化前必须先读”的执行规范：

1. `智能运营分析项目_UI优化参考图与当前功能差异分析说明文档_v20260621.docx`：用于判断目标 UI 长什么样、当前项目已实现什么、缺什么、哪些页面优先级更高。
2. `智能运营分析项目_P6_UI与功能排版优化落地方案_Codex版_v20260622.docx`：用于指导 Codex/开发代理按 UI-0 到 UI-4 分阶段落地，明确技术栈、组件、接口、安全边界、验收标准和不可做事项。

本文件不是替代源文档，而是每次 UI 优化前的强制入口。任何优化任务都必须先读本文件，再根据目标页面精确查阅源文档对应章节，最后再进入代码修改。

## 1. 每次优化前的强制阅读顺序

### 1.1 必须先读

每次涉及 UI/排版/组件/页面重做/参考图复刻时，必须按以下顺序读取：

1. 读取本文件，确认本次任务属于哪个页面、哪个阶段、哪些约束。
2. 读取本次用户提供的目标 UI 参考图或截图，确认画板尺寸、页面结构、区块顺序、信息密度、颜色、间距、卡片比例、图表位置和右侧洞察区域。
3. 读取 `UI优化参考图与当前功能差异分析说明文档_v20260621.docx` 中对应页面章节，确认：
   - 参考图功能是什么；
   - 当前项目已经实现什么；
   - 当前还缺什么；
   - 数据/API 是否支撑；
   - 落地判断和优先级。
4. 读取 `P6_UI与功能排版优化落地方案_Codex版_v20260622.docx` 中对应阶段和页面章节，确认：
   - 应该属于 UI-0 / UI-1 / UI-2 / UI-3 / UI-4 哪一阶段；
   - 应复用哪些组件、接口和设计 token；
   - 是否需要后端/API 最小增强；
   - mock/fallback/derived 是否必须显式标识；
   - 验收与回归门禁是什么。
5. 读取当前仓库真实页面、路由、共享组件、API service、后端接口和数据结构。

未完成以上阅读，不得开始写代码或修改页面。

### 1.2 推荐检索方式

不要每次盲目通读所有大文档。应根据页面关键词聚焦检索：

```bash
# 示例：优化首页/总览驾驶舱

# 示例：优化预测中心 24 小时预测
rg -n "预测中心|24小时预测|ForecastCenterPage|forecastApi|PriceCurveChart|置信区间|低价窗口|高风险" docs frontend/src backend/app

# 示例：优化 AI 助手
rg -n "AI助手|智能问答|AssistantPage|answer_chat_accurate|RAG|Trace|fallback|证据链" docs frontend/src backend/app
```

## 2. 两个核心源文件的职责分工

### 2.1 差异分析文档：先判断“做什么、差在哪、能不能落地”

`UI优化参考图与当前功能差异分析说明文档_v20260621.docx` 的作用是建立目标与现实的对照基线。它明确指出：

- 参考图不是单纯视觉美化稿，而是一套运营型产品目标态。
- 目标 UI 由统一框架、业务筛选、KPI、图表、明细表、右侧洞察/状态/快捷操作、审计和复核闭环组成。
- 当前项目已经具备 FastAPI、React/TypeScript、PostgreSQL、Redis/Celery、P1 数据可信、P2 回测产物、P3 RAG/BGE、P4 任务中心、P5 前端与 AI 体验基础。
- 核心风险不是能不能画出来，而是是否正确区分真实数据、派生数据、mock/fallback，以及审批、复核、模型生命周期是否真的有后端状态机。
- 建议先做全局布局和高价值首屏，再做数据可信、预测可信、AI 结构化回答、任务总览，最后推进报告审核、策略复核、模型晋升/回滚等闭环。

使用规则：

- 每次优化某个页面时，必须先看该页面在差异分析文档中的“参考图功能 / 当前已实现 / 需要补充 / 数据/API 支撑 / 落地判断 / 优先级”。
- 不得只看参考图表面样式就直接重画页面。
- 不得把文档中明确标注为“需要后端补齐”的功能做成假按钮或假闭环。

### 2.2 落地方案文档：再判断“怎么做、分几步、怎么验收”

`P6_UI与功能排版优化落地方案_Codex版_v20260622.docx` 的作用是给 Codex/开发代理直接执行。它要求：

- 不推翻现有技术栈，只在 React 18 + TypeScript + Vite + Ant Design + ECharts + FastAPI + PostgreSQL + Redis/Celery 内优化。
- 优先复用现有组件和接口。
- 不允许为了参考图好看而伪造未部署组件、放宽 SQL 安全或隐藏 fallback 风险。
- 按 UI-0 -> UI-1 -> UI-2 -> UI-3 -> UI-4 分阶段推进。
- 每阶段必须先检索仓库已有组件、页面、API 文件，先给修改文件清单和风险点，再动代码。
- 每阶段完成后必须独立 commit，并运行前端 build 和相关后端/接口回归。
- 所有 mock、fallback、派生数据必须在 UI 上显式标识。
- 没有真实后端状态机的功能只能做“待接入/演示态”，不得假装具备生产闭环。

使用规则：

- 每次开发前先确定当前任务属于哪一阶段。
- 当前阶段之外的内容不得随意夹带。
- 如果同类 UI 出现超过两次，必须抽象复用组件。
- 每个页面都要能回答：当前状态是什么、风险在哪里、依据是什么、下一步能做什么。

## 3. 总目标态

P6 的目标不是把页面“装饰得好看”，而是把当前项目从“功能型后台”升级为“AI 售电交易运营决策工作台”。每个页面都必须做到：

1. **统一**：全局框架、导航、顶部栏、筛选区、KPI、卡片、表格、图表、空态一致。
2. **可信**：数据源、模型版本、更新时间、fallback/mock/派生状态可见。
3. **可行动**：每页都有刷新、导出、生成、复核、查看依据、重试、回滚等上下文动作。
4. **可追溯**：报告审核、策略复核、模型切换、配置修改等关键操作要预留或写入审计。
5. **可扩展**：新增页面复用 AppShell、MetricCard、SectionCard、InsightPanel、TableCard、DetailDrawer、StatusBadge、SmartEmpty 等组件。

## 4. 全局 UI 设计语言

### 4.1 基础框架

所有页面统一采用：

```text
固定左侧导航 + 顶部全局状态栏 + 页面标题/筛选条 + KPI 区 + 主内容网格 + 右侧洞察/状态/快捷操作
```

导航分组建议：

- 业务中心：首页、数据中心、预测中心、策略中心、报告中心。
- 智能应用：AI 助手、知识库。
- 运营管理：模型中心、任务中心、系统设置。

### 4.2 视觉规范

- 主色：`#0FB98A` / `#087A5B`，用于健康、成功、主按钮、当前导航高亮。
- 预测/模型色：`#2F80ED`，用于预测曲线、模型状态、信息提示。
- 提醒色：`#F59E0B`，用于待审核、需关注、降级、fallback。
- 风险色：`#EF4444`，用于高风险、失败、驳回、危险操作。
- 页面背景：`#F6F8FA`。
- 卡片背景：`#FFFFFF`，使用 1px 浅边框和轻阴影。
- 圆角：按钮 8-10px，卡片 12-16px，抽屉/大面板 16px。
- 字号：正文 14px，表格 13px，页标题 22-24px，KPI 数值 24-30px。
- 间距：8px 基准栅格，页面 padding 24px，卡片 gap 16/20px，表格行高 44px。

### 4.3 页面布局原则

每个页面都要避免“只有大表”“只有图”“只有堆叠卡片”。标准页面应包含：

1. 页面标题和业务说明。
2. 业务筛选栏。
3. 顶部 KPI 卡片。
4. 主图或主表。
5. 右侧洞察、状态、证据链或快捷操作。
6. 下方明细表、趋势、任务、日志或补充说明。

## 5. 布局、边界与响应式硬性要求

这些要求是为了防止页面看起来“没铺满、贴边、截断、错位、重叠、空白浪费”。所有页面必须遵守。

### 5.1 整体铺满与安全边界

- 页面在浏览器打开后应尽量铺满可视区域，主体内容充分利用屏幕宽度和高度。
- 四周必须保留统一、安全、适度的外边距，不能贴边、硬截断、边缘生硬或内容顶到屏幕边。
- 左侧导航、顶部栏、主内容区、卡片区和图表区要形成清晰版心关系。
- 页面背景、卡片边界、圆角、阴影、留白必须统一。

### 5.2 板块等距与网格稳定

- 各子板块、卡片、图表、表格、筛选栏、操作按钮之间必须统一等距。
- 优先使用统一 spacing token 或 CSS Grid/Flex `gap`。
- 禁止通过随意 margin 拼接页面。
- 禁止组件重叠、错位、压线、上下左右不齐、间距忽大忽小。
- KPI 卡片、主图、右侧栏、下方卡片的高度和列宽应按参考图比例组织，不得随意拉伸。

### 5.3 内容自适应

- 每个组件内部内容必须跟随所在子块尺寸自适应。
- 标题、指标、图表、表格、标签、按钮必须在容器内完整、有序展示。
- 禁止文本、图表、按钮溢出卡片边界。
- 文本过长时使用省略、换行、tooltip、展开详情或抽屉。
- 图表容器必须监听尺寸变化并自适应重绘，避免图例覆盖、坐标轴文字重叠、曲线截断。

### 5.4 内部滚动与内容过载

- 内容较多的表格、日志、洞察列表、任务列表、AI 建议区，应优先使用卡片内部滚动、折叠、分页或“查看更多”。
- 不得用撑爆页面、遮挡相邻模块或制造横向滚动来解决内容过载。
- 页面级纵向滚动只允许在内容确实超出首屏时出现，不能掩盖首屏关键布局错乱。
- 桌面端页面原则上不得出现横向滚动条；表格可以内部横向滚动，但不能让整个页面横向滚动。

### 5.5 顶部空间利用

- 顶部区域不得浪费大块空白。
- 若顶部存在可用空间，应合理承载项目选择、数据时间、地区、模型版本、筛选条件、主要操作按钮、系统状态、刷新入口等。
- 全局顶部栏负责全局状态，页面 FilterBar 负责业务筛选；不要把所有业务筛选无序塞进全局顶部栏。
- 顶部按钮应按优先级排列：主按钮用于生成/发布/启动，次按钮用于刷新/导出/详情，危险按钮用于驳回/禁用/回滚。

### 5.6 非全屏与常见宽度适配

必须检查：

- 全屏窗口。
- 非全屏窗口。
- 1920px 宽屏。
- 1440px 常用桌面。
- 1366px 笔记本宽度。
- 浏览器缩放后的情况。

在这些场景下，页面都要保持完整、整齐、可读。必要时使用响应式换行、列数调整、卡片堆叠、内部滚动，而不是裁切或遮挡。

## 6. 分阶段路线

### UI-0：统一页面骨架

目标：先让所有页面长在同一套规则上，解决错位、溢出、大片空白、缩放异常和风格断裂。

范围：

- AppShell。
- Sidebar 导航分组。
- HeaderBar 顶部全局栏。
- PageHeader。
- FilterBar。
- MetricCard。
- SectionCard。
- TableCard。
- DetailDrawer。
- 状态色、空态、基础 tokens。

验收：

- 导航高亮准确，折叠状态不丢图标和 tooltip。
- 顶部栏高度稳定，刷新、用户菜单、通知样式一致。
- 任意页面标题、按钮、筛选区对齐。
- 1366px 下不出现页面主体横向溢出。

### UI-1：高价值首屏

目标：优先重做最常打开、已有真实接口、收益最大的页面。

范围：

- 首页 / 总览驾驶舱。
- 数据中心 / 数据总览。
- 预测中心 / 24 小时预测。
- 任务中心 / 总览。

要求：

- 首页首屏展示供需风险、预测可信度、策略预计收益、报告待审、任务提醒、数据健康、AI 建议、策略执行、快捷入口。
- 数据中心集中展示数据源数量、同步任务、异常表、完整率、昨日更新量、接入流程、同步记录、健康摘要。
- 预测 24h 展示最高价、最低价、均价、峰谷价差、可信度、预测曲线、置信区间、低价窗口、高风险窗口、右侧洞察和明细表。
- 任务中心优化空态、任务健康、失败重试、队列概览、日志入口。

### UI-2：可信与 AI 能力

目标：强化数据可信、预测可信、RAG 可观测和 AI 结构化输出。

范围：

- 数据质量 / 数据目录。
- 预测峰谷分析 + 模型评估。
- AI 助手。
- 知识库 / RAG。

要求：

- 数据质量展示缺失率、重复率、新鲜度、校验通过率、异常明细、目录卡片、字段预览、血缘和用途说明。
- 预测模型评估展示 baseline、schema、leakage、backtest、训练状态，但不得宣称模型精度已大幅提升。
- AI 助手采用三栏结构：会话列表、结构化回答、右侧证据链；普通用户默认隐藏 Trace。
- 知识库展示文档数、chunks、待处理、QA 通过率、RAG provider、embedding_dim、fallback/降级原因、检索测试和索引刷新。

### UI-3：审批与生命周期

目标：补齐报告审核、策略复核、模型上线/回滚等半闭环能力。

范围：

- 策略中心 / 总览。
- 策略中心 / 人工复核。
- 报告中心 / 列表预览。
- 报告中心 / 审核发布。
- 模型中心 / 生命周期。

重要边界：

- 只要按钮会改变业务状态，就必须有真实 API、数据库字段、权限校验和审计记录。
- 没有真实后端状态机时，只能展示“待接入/演示态”，不能假装完成审批或发布。

### UI-4：业务执行增强

目标：增强生产化执行能力。

范围：

- 储能 SOC 与执行清单。
- 真实上一批次预测对比。
- 策略收益回填。
- 任务 SLA 与失败聚类。
- 真实服务健康和监控告警。

要求：

- 真实上一批次预测对比需要 forecast_runs 持久化和 compare API。
- 策略执行清单和收益回填需要后端表或字段支撑。
- 监控只接真实服务：PostgreSQL、Redis、Celery、RAG/BGE、LLM、日志/审计；不得伪造 Kafka、Airflow、MinIO、Prometheus、ELK 等当前未部署组件。

## 7. 页面级执行索引

### 7.1 全局框架层

当前基础：已有 BasicLayout、HeaderBar、Sidebar、PageContainer、10 个一级页面、用户登录态、模型版本/数据时间等头部概念，以及 MetricCard、SectionCard、TableCard、DetailDrawer、状态/空态组件。

必须优化：

- 导航分组。
- 顶部项目/时间/地区/模型/系统状态栏。
- 全局搜索、通知中心、用户菜单。
- 页面筛选条。
- KPI 卡片、图表区、任务/告警/快捷入口统一。
- 页面缩放、卡片松散、浏览器通知遮挡、边界不整齐问题。

### 7.2 首页 / 总览驾驶舱

当前基础：DashboardPage 已有指标卡、风险列表、24 小时电价趋势、储能建议、最新报告、任务日志、快捷操作；dashboardApi 汇总 forecastLatest、tasks、dataFreshness、tasksHealth、knowledgeHealth、dbHealth、modelBacktestSummary。

必须优化：

- 取消分散 Tab 感，首屏完成核心运营驾驶舱。
- 顶部 KPI：今日供需风险指数、预测可信度、策略预计收益、报告待审、任务提醒、数据健康。
- 主图：24 小时供需风险总览，包含预测电价、负荷、新能源/可用性、低价窗口、高风险时段。
- 右侧：AI 建议摘要、策略执行摘要、任务提醒。
- 下方：关键预测指标、模型状态、数据健康、最新报告、快捷入口。

## 8. 数据、mock、fallback 与安全约束

### 8.1 数据可信规则

- 所有页面必须能说明数据来自哪里：PostgreSQL、postgresql_or_file、mock_fallback、derived、RAG、只读 SQL、后端工具等。
- fallback/mock/derived/降级状态必须显式标识，且使用提醒色，不得用绿色“正常”掩盖。
- 数据库不可用、RAG 维度不一致、LLM fallback、任务中心空记录、接口错误都必须给出原因和下一步动作。
- 业务用户应能判断结果是否真实、是否派生、是否只读 SQL 查询、是否 RAG/LLM 生成。

### 8.2 安全边界

禁止：

- 放宽 P1 只读 SQL 安全策略。
- 在普通用户视图默认展示 Trace、工具日志、密钥、token、数据库连接串。
- 把 mock/fallback 显示为真实生产数据。
- 伪造未部署中间件或外部系统。
- 为按钮做假交互。
- 把 P2 baseline 指标包装成模型效果已大幅提升。
- 批量或递归删除文件。

### 8.3 状态机边界

涉及以下操作时，必须有真实 API、数据库字段、权限校验和审计记录：

- 策略通过/驳回/复核。
- 报告审核/发布/归档/驳回。
- 模型设为 Active、回滚、注册 Candidate。
- 执行清单状态变更。
- 用户、权限、系统配置变更。

没有真实状态机时，只能显示“待接入/演示态/只读预览”。

## 9. 开发执行流程

### 9.1 建立事实基线

开始任何页面改造前，必须先输出：

1. 本次目标页面。
2. 目标参考图对应章节。
3. 当前页面路由。
4. 当前组件和布局。
5. 当前 API service。
6. 当前后端接口。
7. 当前真实数据字段、单位、时间范围。
8. 当前加载态、空态、错误态。
9. 拟修改文件清单。
10. 缺失接口、派生数据、mock/fallback、状态机风险。

### 9.2 选择改造方式

- 用户要求“重做、重构替换、1:1 复刻”时，整页重写业务页面 DOM/layout。
- 不得继续沿用与参考图冲突的旧排版逻辑。
- 删除旧页面布局依赖时，只移除明确旧代码，不批量删除目录。
- 优先复用设计 token、AppShell、全局导航和基础组件。
- 如果现有组件和参考图冲突，优先按参考图结构重排，再抽象组件。

### 9.3 实现页面

- 以参考图为视觉和结构主准绳，以真实项目 API 和业务能力为功能边界。
- 使用 CSS Grid/Flex 建立稳定结构，避免绝对定位拼图。
- 无 API 时先补后端接口或标注待接入；禁止硬编码业务记录替代。
- 内容过多的表格、洞察栏、日志、任务列表使用内部滚动，不用页面级滚动掩盖排版问题。
- 普通用户页面优先展示业务结论、风险、依据、下一步动作；技术 Trace 默认隐藏。

## 13. 最终原则

每次 UI 优化都必须先回到这三个问题：

1. **目标参考图要表达的业务结构是什么？**
2. **当前项目真实具备什么能力，缺什么接口或状态机？**
3. **本次改动是否让页面更统一、更可信、更可行动、更可追溯，而不是只变得更花哨？**

只有这三个问题都有明确答案，才能开始动代码。
