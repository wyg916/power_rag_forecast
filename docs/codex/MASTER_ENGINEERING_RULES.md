# MASTER_ENGINEERING_RULES.md

# 一、规则优先级
优先级从高到低：
1. 用户在当前任务中的明确指令；
2. 根目录 `AGENTS.md`；
3. 本文件；
4. 当前任务文件；
5. 项目既有开发习惯。
出现冲突时，执行更安全、更小范围、可回滚的规则，并说明冲突。

# 二、Token 与上下文预算
## 2.1 任务粒度
- 一个任务只解决一个主目标，最多包含一个直接从属目标。
- 禁止以“顺手优化”为由修改无关代码。
- 对大型任务先按接口、数据库、服务、测试拆成检查点，不要一次改完整仓库。

## 2.2 检索策略
- 首先读取基线摘要、当前任务文件和已有状态记录。
- 使用 `rg`/符号搜索定位目标；仅在定位失败时扩大范围。
- 不重复读取已确认无关的大型目录、构建产物、虚拟环境、node_modules、模型二进制、备份目录和历史归档。
- 默认排除：`.git`、`.venv`、`venv`、`node_modules`、`dist`、`build`、`__pycache__`、`.pytest_cache`、`backups`、模型大文件和日志归档。

## 2.3 输出预算
Codex 对话回复只保留：
1. 结论；
2. 修改文件；
3. 测试结果；
4. 风险/停止项；
5. 回滚路径；
6. 下一步。
完整命令输出、diff、测试日志写入任务证据目录，不在回复中重复粘贴。

# 三、备份与回滚规范
## 3.1 首次阶段基线
在任何业务修改前创建：
`backups/phase3/<timestamp>_BASELINE/`
至少包含：
- `git_status.txt`
- `git_diff.patch`
- `untracked_files.txt`
- `tracked_files_manifest.csv`
- `critical_hashes.sha256`
- `environment_summary.txt`
- `database_schema_only.sql`（获得授权且数据库可用时）
- `RESTORE.md`
不得清空已有备份。

## 3.2 单任务检查点
每个 T00X 任务创建：
`backups/phase3/<timestamp>_T00X_PRE/`
只做增量备份：任务涉及文件原件、diff、状态、数据库影响和回滚命令。除首次基线外，不重复压缩整个仓库，以降低时间和磁盘消耗。

## 3.3 回滚门槛
任务完成前必须至少验证一种回滚：
- Git patch/commit 回滚；
- 文件级恢复；
- Alembic downgrade；
- 事务回滚；
- 配置恢复。
不能验证回滚时，交付状态标记为“未完成/等待人工确认”。

# 四、磁盘与文件保护
## 4.1 允许范围
默认允许读写：项目根目录及其明确子目录。
建议新增临时目录：
- `.codex_tmp/`
- `backups/phase3/`
- `docs/codex/evidence/`
这些目录必须位于项目盘。

## 4.2 C 盘规则
- C 盘只允许读取运行必需的系统工具路径。
- 禁止在 C 盘创建项目备份、缓存、模型、数据库、日志、虚拟环境或下载文件。
- 禁止修改 Windows 注册表、计划任务、系统服务、系统环境变量、用户全局配置。
- 如工具默认写 C 盘缓存，先改为项目内临时目录；无法改写时停止并请求确认。

## 4.3 删除与覆盖
未经确认禁止：
- 删除任何已有源代码、配置、模型、数据库、文档和历史产物；
- 重命名或移动公共入口；
- 覆盖原文件且不保留备份；
- 清理 untracked 文件；
- 批量格式化整个仓库。
允许新增文件，但必须位于任务允许范围，并在交付清单中列出。

# 五、数据库安全
- 自 2026-07-26 起，后续开发、调试和自动化测试唯一允许连接现有 Navicat `dianli` 对应的 PostgreSQL：`localhost:5432/postgres`，用户 `postgres`；该用户明确约束优先于早期“默认隔离库”规则。
- 数据库密码仅从本地安全环境变量或未纳入版本控制的本地配置读取；禁止写入代码、测试、Markdown、日志、截图或 Git。
- 测试与工具必须先校验 host、port、database、username，目标不匹配时 fail-closed；不得自行创建或改用其他数据库。
- 禁止无 WHERE 的 UPDATE/DELETE、TRUNCATE、DROP、全表覆盖、先删后插式同步。
- 迁移必须有 upgrade/downgrade，并在目标库执行前建立结构、行数、关键约束与受保护表检查点。
- 写链必须事务化，失败无半成品。
- 数据库变更前记录表结构、行数和关键约束；变更后复核。

## 5.1 缺失业务数据模拟规则
- GET/查询接口不得产生 seed、激活、同步或其他写副作用。
- 不得把 seed/demo/fallback/历史数据伪装为实时真实数据。
- 所有前端业务页面不得展示“模拟数据”“真实数据”“模拟入库”等数据来源分类文案，也不得直接展示 `data_source`、`source_type`、`is_simulated` 等技术追溯字段；前端应使用中性的业务名称、业务时间、更新时间和状态语义呈现数据。
- 前端隐藏来源分类不等于删除追溯信息：数据库、后端领域服务、API 契约、日志和审计记录仍必须完整保留来源、模拟标识、批次、生成时间和场景等元数据，供权限受控的排障与审计使用。
- 页面所需数据缺失时，只允许按真实业务字段、约束和计算规则生成受控数据，并严格经过“受控生成程序 → PostgreSQL → 后端领域服务/Repository → API → 前端状态与组件”链路；禁止在前端生成、硬编码或用接口失败后的成功态 fallback 补齐业务数据。
- 受控生成记录至少包含 `data_source`、`is_simulated`、`batch_id`、`generated_at`、`scenario`；批次必须幂等、可精确识别、可按批次回滚，且不得覆盖非受控生成记录。
- 前端仍必须如实呈现 Loading、Empty、Error、Stale、Unauthorized、Forbidden 等状态以及业务时间/更新时间；不得把过期、测试或受控生成结果明示为实时设备采集、真实交易执行或真实结算结果。
- 自动交易、设备控制、资金动作仍为禁止项；受控生成的执行反馈只能作为只读运营事实或决策支持数据。

## 5.2 企业级等价、RAG 与启动器口径
- “企业级等价”表示在当前本地资源和已部署能力内，按企业级安全、审计、可回滚和失败关闭原则实现；不得等同于生产 SLA、生产容量或生产发布许可。
- “RAG 已接入”必须区分语料治理、PostgreSQL 元数据、Qdrant Collection、检索、重排、引用和发布状态；仅有检索代码或 Candidate 数据不得宣称完整 RAG 闭环。
- `run_project.bat` 是唯一 RC 默认双击入口；必须展示分支、提交、日志路径和失败码，且启动过程不得隐式同步业务数据、执行迁移、Seed、激活模型或发布 RAG。
- 启动器只可复用健康服务或启动缺失服务，不得自动终止未知端口进程，不得自动联网安装依赖。
- RC 合入仅允许按批准白名单和来源提交执行；每次集成必须记录来源 SHA、目标提交、冲突处置、测试证据与回滚路径。


# 六、模型与数据安全
- 未获用户明确授权，不反序列化 joblib/pickle 等模型二进制。
- 授权后也仅在无网络、只读模型挂载、隔离输出环境中验证。
- 加载前校验 hash、manifest、运行时版本和 schema。
- Candidate 通过验证后仍需人工确认才可晋升 Active。
- 输入契约异常必须停止；不得静默补 0 或跨表/跨业务域回退。

# 七、变更控制
## 7.1 修改上限
单任务预计超过 20 个文件或 1000 行有效代码，必须先拆分并请求确认。
## 7.2 公共接口
更改 API、数据库表、配置项、任务名称、模型状态或前端契约时，必须说明兼容策略。
## 7.3 完成定义
只有满足任务验收标准、相关测试通过、回滚可用、证据落盘，才能标记完成。

# 八、证据与审计
每项任务输出到：
`docs/codex/evidence/T00X_<timestamp>/`
至少包含：
- `plan.md`
- `changed_files.txt`
- `commands.txt`
- `test_summary.md`
- `rollback.md`
- `unresolved.md`
- 必要的结构化日志或截图路径
禁止在证据中写入密码、Token、API Key 或完整连接串。
